# Kyiv power group 47.1 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A macOS menu-bar item and a cloud Telegram notifier for the YASNO outage schedule of Kyiv group 47.1.

**Architecture:** One small stdlib-only Python package `power/` shared by both parts. The cloud part is a GitHub Actions workflow (every 10 min) that fetches YASNO, diffs against `state.json` committed in the repo, sends Telegram messages, and commits the new state. The Mac part is a SwiftBar plugin that imports the same package, fetches YASNO directly, and checks the cloud's last successful run via the public GitHub API.

**Tech Stack:** Python ≥ 3.9 (stdlib only: `urllib`, `json`, `zoneinfo`, `datetime`), `unittest`, GitHub Actions, SwiftBar.

**Spec:** `docs/superpowers/specs/2026-11-06-kyiv-power-47-1-design.md`

## Global Constraints

- Group `47.1`; URL `https://app.yasno.ua/api/blackout-service/public/shutdowns/regions/25/dsos/902/planned-outages`.
- Time zone `Europe/Kyiv` for every "now", date and 22:00 decision; never a fixed UTC hour.
- Daily message at Kyiv local time ≥ 22:00, for tomorrow's date, always sent (even if tomorrow already arrived as a change).
- Changes to today or tomorrow are notified at any time of day; `updatedOn` is ignored; state is keyed by calendar date (midnight rollover is not a change).
- Messages in Ukrainian. Wording fixed by spec: `🗓 Графік на завтра, <день тижня> <D> <місяця> (група 47.1)`, `🕯 HH:MM–HH:MM`, `❓ HH:MM–HH:MM` (possible), `⚠️ Аварійні відключення, графіка немає`, `⏳ Графіка на завтра ще немає`, `🔄 Графік на <сьогодні|завтра> змінився` + `Було:` / `Стало:`, `❗ Не можу отримати графік з YASNO`, `✅ Графік з YASNO знову доступний`.
- Failure message after 3 consecutive failed fetches; once per outage; recovery message once.
- Secrets only as env `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` (GitHub Actions secrets). Never printed, never committed.
- Repo: new public `mozol0403/kyiv-power-47-1`. No third-party Python dependencies.
- Menu bar: refresh every 5 min; title `⚡ до HH:MM` / `🕯 до HH:MM` / `⚡` / `⚠️ аварійні` / `❔`; dropdown warns `⚠️ Telegram-сповіщення не працюють з HH:MM` when no successful cloud run for > 1 h. The Mac sends no notifications.

## Review Focus

1. YASNO answers 200 but with HTML (anti-bot page), invalid JSON, or without key `47.1` → treated as a failed fetch (failure counter), never as "schedule cleared" (no change message, state untouched). Test in Task 2 and Task 5.
2. A slot ending at 1440 or a schedule whose last outage ends at midnight → printed as `24:00`; menu-bar "next change" crosses into tomorrow correctly. Test in Task 3 and Task 6.
3. Telegram send fails (revoked token, network) → the run exits non-zero, state for that message is not advanced, so the next run retries. Test in Task 5.
4. Two workflow runs overlapping, or the state push being rejected → `concurrency` group, `git pull --rebase` and one retry. Covered in Task 7 workflow.
5. First run with empty state, or a newly seen date that is `WaitingForSchedule` / `EmergencyShutdowns` → silent baseline, no message (otherwise every midnight would notify). Test in Task 4.

## File structure

```
power/__init__.py
power/schedule.py     # fetch + normalize YASNO data → Days
power/text.py         # Ukrainian formatting of days and changes
power/diff.py         # compare stored vs new Days → list of Change
power/telegram.py     # send a message
power/cloud.py        # one cloud run: state in, messages out, state out; CLI entry
power/menubar.py      # SwiftBar output
swiftbar/power47.5m.py  # thin SwiftBar wrapper (symlinked into the SwiftBar plugin folder)
state.json            # committed by the workflow
.github/workflows/check.yml
.github/workflows/keepalive.yml
tests/test_*.py
README.md             # setup: bot, secrets, SwiftBar
```

Data shapes used across tasks (define in `power/schedule.py`):
- `Slot = tuple[int, int, str]` — `(start_min, end_min, kind)`, kind ∈ `"definite" | "possible"`.
- `Day = dict` — `{"status": str, "off": list[[start, end, kind]]}` (JSON-serialisable; lists, not tuples, when stored).
- `Days = dict[str, Day]` — keyed by ISO date `"YYYY-MM-DD"` in Kyiv time.

### Task 2: Fetch and normalize (`power/schedule.py`)

**Interfaces — Produces:**
- `URL: str`, `GROUP = "47.1"`, `KYIV = ZoneInfo("Europe/Kyiv")`
- `class FetchError(Exception)`
- `fetch_raw(url: str = URL, timeout: int = 20) -> dict` — raises `FetchError` on network error, non-200, non-JSON, or JSON that is not an object.
- `normalize(raw: dict, group: str = GROUP) -> Days` — raises `FetchError` if `group` missing or a day lacks `date`/`status`.

Normalization: date = `date[:10]` of each of `today`/`tomorrow`; slot type `Definite` → `"definite"`, `NotPlanned` → dropped, any other type → `"possible"`; slots sorted by start; status kept raw.

### Task 3: Ukrainian text (`power/text.py`)

**Interfaces — Consumes:** `Day`, `Days`. **Produces:**
- `hhmm(minutes: int) -> str` — `480 → "08:00"`, `1440 → "24:00"`.
- `day_lines(day: Day | None) -> list[str]` — `🕯`/`❓` interval lines; `["⚠️ Аварійні відключення, графіка немає"]` for `EmergencyShutdowns` with no slots; `["⏳ Графіка ще немає"]` for `None` or `WaitingForSchedule`; `["⚡ Відключень немає"]` for `ScheduleApplies` with no slots; `[f"Статус YASNO: {status}"]` for any other status with no slots.

Ukrainian weekday abbreviations `пн вт ср чт пт сб нд`; months in genitive `січня … грудня`.

### Task 4: Change detection (`power/diff.py`)

**Interfaces — Produces:**
- `Change = tuple[str, Day | None, Day]` — `(date, old, new)`.
- `changes(old: Days, new: Days) -> list[Change]` — sorted by date.

Rules: date in both and `old != new` → change. Date only in `new`: change only if `new[date]["off"]` is non-empty (a published hourly schedule); otherwise silent. Dates only in `old` → ignored. `old == {}` (first run) → `[]`.

### Task 5: Cloud run (`power/telegram.py`, `power/cloud.py`)

**Interfaces — Consumes:** Tasks 2–4. **Produces:**
- `send(text: str, token: str, chat_id: str) -> None` — POST `https://api.telegram.org/bot{token}/sendMessage`; raises `RuntimeError` (message without the token) unless `"ok": true`.
- `run(state: dict, now: datetime, fetch: Callable[[], Days], send: Callable[[str], None]) -> dict` — returns the new state. State keys: `days: Days`, `daily_sent: str | None`, `fail_count: int`, `fail_notified: bool`.
- `main() -> int` — reads/writes `state.json` in CWD, env secrets, `now = datetime.now(KYIV)`; if env `FORCE_DAILY=1`, sets `daily_sent = None` and `now` to today 22:00 Kyiv before calling `run` (one-off test from Task 7); returns 0, or 1 if any send raised (after saving whatever state was reached).

`run` order: fetch (on `FetchError`: `fail_count += 1`; if it reaches 3 and not `fail_notified` → send failure text, set flag; return without touching `days`/`daily_sent`). On success: if `fail_notified` → send recovery text; reset counters. For each change → send `change_message` (label from today/tomorrow date in Kyiv) and only then write that date into `state["days"]`. Then, if `now.hour >= 22` and `daily_sent != tomorrow` → send `daily_message(tomorrow, days.get(tomorrow))`, then set `daily_sent`. Finally replace `days` with fetched days restricted to dates ≥ today. A raising `send` propagates after the state reached so far is kept, so unsent items are retried next run.
